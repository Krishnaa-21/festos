FESTOS SHARED CONTEXT v1.0. Every agent session reads this first. Change it
only through a PR labelled `context`.

1. PRODUCT PRINCIPLES
- FestOS is the internal command centre for the Aarohan fest (EPINOIA 2026,
IIM Indore). It is not a registration site and not a CRUD portal. Scale:
~2,400 expected vs 2,836 raw participants (never force 2,400: reconcile and
show the gap), 38 contingents, 31 events, 9 venues, 14 vendors, 48 core team,
200 rooms / 710 beds on campus, 6 external properties / 740 beds.
- A change is complete only when its downstream effects are visible.
- AI proposes. Deterministic logic validates. Humans approve.
- UNKNOWN is a first-class value. A blank never means NO, consent, a gender,
dietary clearance or absence of need.
- Hard constraints (accessibility, privacy, safety, required housing
preference) are never auto-relaxed. Soft constraints are relaxed only with a
recorded reason, in this order: cohesion, cost, proximity.
- Every mutation goes through ChangeService. Every important decision has a
Why card. Every high-risk override lands in the override register.
- Assumptions are visible, editable, owned and sourced. Heuristics are never
called optimal. Schedules generated by FestOS are labelled ASSUMED. Synthetic
data only.
- Reference numbers in the spec (1,601 peak beds, 987 unscheduled
registrations, 71 minors external, ...) come from an earlier prototype. Use
them as sanity checks, never hardcode them.

4. CODING STANDARDS
- Python snake_case, classes PascalCase, type hints everywhere, ruff + black.
Routers call services, services call engines. No business logic in routers.
Engines are pure and unit-tested.
- JSON keys are snake_case. TypeScript API types are generated (`make gentypes` writes frontend/src/types/generated.ts), never hand-copied. React
components PascalCase, hooks useX, one feature folder per module slug.
- Module slugs (used for api file, service dir, feature dir, permission
prefix, docs/api file): auth audit approvals overrides imports assumptions
participants contingents reconciliation unknowns accommodation checkin events
venues schedule logistics merchandise vendors food finance staff transport
notifications incidents impact scenarios premortem forecasting dashboard
decisions commands reports
- IDs: keep source IDs (C05, VND05, ...) as primary keys where the data pack
has them; otherwise prefix + zero-pad. Raw rows are preserved in raw_record;
canonical rows keep source_row_id.
- Time: store UTC timezone-aware, display Asia/Kolkata. core.clock.now() is
the only source of the current time (supports FESTOS_NOW env and a demo-time
endpoint).

5. API CONVENTIONS
- Base path /api/v1/<module>. Success envelope: {data, meta, warnings}. Error
envelope: {error: {code, message, details, request_id}}.
- Error codes: VALIDATION_ERROR, NOT_FOUND, FORBIDDEN, UNAUTHENTICATED,
VERSION_CONFLICT (409), ALREADY_ISSUED (409), CONSTRAINT_VIOLATION (422,
details = Violation list), APPROVAL_REQUIRED (202), RATE_LIMITED, INTERNAL.
- Lists accept page, page_size, sort, q plus filters, and return meta.total.
- Mutating requests: `Idempotency-Key` header (mandatory for scan, issue,
check-in, sync and commit endpoints); optimistic concurrency through
`expected_version` in the body (409 VERSION_CONFLICT). Bodies may carry
`reason`. `dry_run=true` returns the impact preview and writes nothing.
- Sensitive fields (contact, medical, accessibility, room data, guardian
data) are masked in serializers by core.masking according to the actor's
role.
- Contract first: before implementing a module, push docs/api/<module>.md
(endpoints, request/response schemas, example JSON) plus Pydantic schema
stubs so the frontend can mock them with MSW.

6. DATA CONVENTIONS
- Tri = YES | NO | UNKNOWN. Categorical fields (gender, diet,
housing_preference, accessibility_need, ...) store the literal UNKNOWN when
missing, never NULL or empty string. field_verification(entity_type,
entity_id, field, status UNKNOWN|CLAIMED|VERIFIED, value, source,
verified_by, verified_at, owner) tracks confirmation.
- Mutable tables carry id, version, created_at, updated_at. Never hard-delete
operational rows; use status.
- Canonical tables (spec section 11): participant, contingent, registration,
event, event_requirement, venue, travel_time, room, external_property,
stay_assignment, inventory_item, inventory_movement, merch_claim, vendor,
vendor_assignment, staff, audit_event, change_set, assumption, override,
incident, approval, shift, transport, shuttle_assignment.
- Prompt 1 additionally creates: user, break_glass_grant, accommodation_plan
(plan_id; kind A|B|C|LIVE; status CANDIDATE|APPROVED|LIVE|ARCHIVED),
event_session, schedule_version, conflict, inventory_location, meal_slot,
import_batch, raw_record, quarantine_row, duplicate_candidate, merge_record,
field_verification, notification_draft, scenario, idempotency_key. Owners may
add more tables inside their own model files.
- Hard DB guarantees: unique(canonical_participant_id, item_id) on
merch_claim; no overlapping active stay for the same bed within a plan;
append-only audit_event.

7. CHANGE SERVICE (every mutation uses it)
Flow: validate -> check constraints -> snapshot previous state -> apply in
ONE transaction -> audit_event + change_set -> impact hook -> recommendations
-> approval gate.
- ChangeRequest{action, entity_type, entity_id, payload, reason, actor,
related_incident_id, expected_version, dry_run, idempotency_key}
- ChangeResult{change_set_id, status
APPLIED|PENDING_APPROVAL|REJECTED|DRY_RUN, violations, audit_event_ids,
impact, recommendations, warnings}
- Handlers register with @register_change_handler('<module>.<verb>') and
implement validate(req, session) -> list[Violation]; snapshot(req, session) -
> dict; apply(req, session) -> dict; risk(req) -> LOW|HIGH; optional
revert(change_set, session).
- HIGH risk returns PENDING_APPROVAL unless the actor's role may approve and
a reason is given. Approvals and overrides are owned by P3 and called through
core interfaces approvals.require(...) and overrides.record(...).
- In-process domain events: core.bus.publish('participant.status_changed',
payload); consumers use @subscribe and must be idempotent.

8. MODULE PUBLIC CONTRACT (the integration glue)
Every module exposes services/<module>/public.py with READ-ONLY functions:
- summary(session, now) -> dict of dashboard KPIs
- risks(session, now) -> list[RiskItem] (evaluated as of `now`, so the premortem can replay any hour)
- dependents(session, entity_type, entity_id) -> list[EntityRef] (what sits
downstream of this entity; feeds the impact graph)
Modules import other modules only through public.py and schemas, never their
internals. Dashboard, impact graph, simulator, pre-mortem and reports read
through these.
Other registries (core/registry.py): register_participant_section(name, fn)
for the participant 360 view; register_seeder(name, order, fn) with `python -
m app.seed reset` rebuilding the DB (order: 10 import, 20 users, 30
accommodation resources, 40 inventory, 50 vendors, 60 staff).
Shared schemas (schemas/common.py): Tri, Severity (1 LOW, 2 MEDIUM, 3 HIGH, 4
CRITICAL), Actor, Violation{code, severity, hard, message, entity_refs},
EntityRef{type, id, label}, RiskItem{id, module, kind, title, severity,
hours_to_impact, people_affected, uncertainty 0-1, resource_criticality 1-5,
entity_refs, action{label, route, api}, explanation},
ImpactReport{root_change, nodes[{type, id, label, severity, people_affected,
depth, parent, status}], counts_by_type, recommendations, before_after},
DecisionCard{id, subject, recommendation, hard_satisfied,
soft_relaxed[{constraint, reason}], alternatives_rejected[{option, why}],
cost_impact, people_affected, approved_by, created_at}, Envelope, Page.

9. SHARED ENUMS AND SCORING
- Roles: FESTIVAL_DIRECTOR, ACCOMMODATION_LEAD, EVENT_LEAD,
LOGISTICS_MANAGER, MERCHANDISE_MANAGER, FOOD_OPS_MANAGER, FINANCE_MANAGER,
VOLUNTEER, AUDITOR. Permission strings: <module>:
<read|write|approve|export|sensitive>.
- Attention score = Severity (1-4) x Urgency x max(people_affected, 1).
Urgency by hours_to_impact: <=1h 5, <=4h 4, <=12h 3, <=24h 2, otherwise or
None 1. core/scoring.py is the single implementation.
- Participant status: EXPECTED, ARRIVED, CHECKED_IN, CHECKED_OUT, CANCELLED,
NO_SHOW, WITHDRAWN, INVALID, MERGED. Plan kinds: A cohesion-first, B costfirst, C balanced.

11. GIT AND INTEGRATION
- Branches: main (demo-ready, protected), develop (integration), pN/NN-slug
feature branches. PRs go to develop only, rebased, squash-merged, reviewed by
another person (cross-owner changes need the owner). develop merges to main
only at checkpoints (end of each round, code freeze).
- backend/requirements.txt has one section per owner (# --- P1 ---, # --- P2
---, # --- P3 ---); append only inside your own section. Frontend
dependencies: PR labelled `deps`; everyone runs `npm ci` after pulling.
Commit lockfiles.
- Env: .env.example is the single source; add every new variable there with a
comment. Never commit secrets. Ports: API 8000, web 5173. DB file
backend/festos.db is gitignored.
- No Alembic. A schema change means editing the model and running `make
reset`. After round 1 only additive columns, announced in team chat. Append
to docs/INTEGRATION_LOG.md after each merge: date, prompt, endpoints,
public.py functions, breaking notes.
- CI must pass: ruff, pytest, tsc --noEmit, vitest, generated types up to
date.

13. SPEC DECISIONS ALREADY MADE (do not reopen)
- Never force 2,400. Show raw 2,836, declared 2,842 and narrative 2,400 with
a reconciliation that explains or flags the remainder.
- One cleaning buffer assumption (default 180 min), shown in the UI.
- Confirmed and possible accommodation demand are always reported separately.
- Three accommodation plans A, B and C (C is new and must be implemented).
- Hard accessibility, safety and privacy constraints can be overridden only
by the Festival Director, with a reason, and always appear in the override
register.
- Late-arrival wave and wildcard finals need Director approval.
- Duplicates are never auto-merged; merges are reversible.
- The pack has no event times, venues, judges or team IDs, so any generated
schedule is labelled ASSUMED and judge slots show as gaps.
- Vendor capacity is evaluated per meal slot, venue and dietary category, not
only in aggregate.
- Zero venue overlaps does not mean zero conflicts: all ten conflict types
are checked.
